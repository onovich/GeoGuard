# 修复方案审议：UI / 输入 / 整体比重

2026-10-06。只审方案，不实现、不新增浏览器操作。依据刚完成的当前真实游戏复核与最新UI正式验收。

**结论：有条件同意。** A先定世界主体、保持现行UI字号和140/8/920合同，随后B/C优化效果与地面，这个顺序正确。现行UI已更可读；继续缩UI来补偿过小身体会回退已通过成果。方案保持原AI/经济/奖励/碰撞，并明确不可裁真实弹体与危区，方向认可。以下三项需写入方案后方可称UI侧技术审议通过。

## 必须修改条件

1. **补960×720较小电脑窗口回归。** A选稿与D最终矩阵目前列1280/1440/2304，遗漏仍属电脑端的960×720。必须增加960 DPR1，DPR2可跟D统一覆盖。重点为真实九塔首末/建造、完整单长Boss与双子、长对策、危区与底栏交叠、奖励modal纵向可达。不是新增手机范围，也不要求完整95技能在四尺寸重复；至少A的四个局面及UI交互在960通过后再批量扩身份。

2. **相机候选倍率写清相对基线。** 当前实现此前已有1.25默认zoom；方案的“相对倍率1.0/1.25/1.5”需明确是相对当前冻结可见尺度，记录最终绝对zoom、单位身体表现因子、当前/修后可见世界范围。否则集成容易把1.25乘两次，最终过度裁场。同一真实输入/阵地取证，并记录被HUD/Boss/底栏遮住的有效可玩窗口；2304是补充宽屏，不能凭它画面宽松替代960/1280判定。

3. **把输入回归写成可执行的通过清单。** 同一world↔screen公式是必要条件，但需要实际验：视口中心与四向邻边处拖放；移动相机后同一世界点；从首/末塔卡起拖；整栏与原18px取消外扩范围释放；不足仍可起拖且释放不扣款；放置时资金/实体距离按原规则；暂停/奖励清drag。记录指针→ghost中心→成功实体root的对齐（允许既有取整，目标不新增超过约1逻辑px误差），圆盘保持正圆、真实半径和owner关系。UI screen尺寸保持原规范，相机仅影响world；不把角色五官bounds当逻辑中心。枪口调整须单独说明视觉锚点与实际projectile逻辑出生坐标如何衔接，保持原伤害/碰撞规则，不以修改弹体起点或碰撞来掩盖对齐问题。

## 已同意且应保留

- PLAYER/BASIC/BURST/普通敌人/双子HIVE竖切片后再覆盖48身份，防止全项目统一盲放大。
- 明确body bounds不含环/HP条，宽度区间为搜索范围；小尺寸五官简化保持器官数量、炮管连接、水平root。
- 字号、原九塔解锁/费用/等级/native横滚、说明真实所属/完全离屏close、教学关闭状态保持，不回滚近期通过项。
- 反馈降采样仅装饰；危险区、独立弹体、实体不能因预算消失；数字合并仅稳定targetId并保存真实总和，状态/治疗/关键攻击不同语义不可混并。
- 相机改变视野需披露屏外行为，不悄悄改生成规则或Boss招式；相同密度同时间性能比对。
- UI组只读验收、共享camera/scene单集成人独占；READY落盘编号返修，保持旧证据。

## 风险与必要证据

- 身体比碰撞几何大，可能在视觉上挡住实际合法空隙。选稿不仅比漂亮截图，还要用成功/失败建造的真实规则验证，解释为何允许身体重叠程度；不增加隐藏碰撞边或偷偷扩大碰撞半径。
- 屏幕最小描边与身体尺度会提高世界视觉重量；HUD对比已分级，不应自动让Boss卡/辅助提示一起加粗。以同场景原尺寸第一眼找到英雄、读取紧迫危区为验收，而非只看角色联系图。
- 现有reward使用CSS subgrid，本轮浏览器扩展不在方案范围，至少记录当前受测Chromium环境；如声称其它浏览器支持需独立验证。不要因为world修复去重写已通过奖励组件。
- B的100–150ms聚合可能造成反馈延迟，必须保留急迫击杀/关键命中即时识别，且验证目标死后未发出的聚合如何清算；这属于表现反馈回归，不修改伤害时刻。
- 三张同类/混合/1/2支持奖、末级RAPID间隔下限保持最新reward-polish收益选择、字段和CTA对齐。正常奖励链/死亡重试可各有真实流程证据，其余合法组合用明确标记的生产组件fixture補证，不能称fixture是实机通关。

以上不要求额外UI美术重做。封面字形与方向键簇延后合理；若完成前三项，本UI组同意进入A的可实施方案，但此审议不等于A实现通过或用户最终验收。
