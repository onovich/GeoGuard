# 真人试玩：单局统计与决策依据

已实现单局JSON采集，schema为 `geoguard-human-playtest-v1`。目标是找出体验与平衡问题的具体发生条件，再决定是否修改引导、Boss、兵线、塔、奖励或经济。数据是研究仪表，包含屏外情况；不可作为受限信息模拟玩家的实时观察接口。

## 玩家怎么使用

开始一局后，点击右侧「试玩数据」。战斗中打开会暂停，返回后恢复打开前的状态；原本暂停或正在选奖励则保持原状态。结算页也有相同入口。复制JSON即可发给研究者，也可下载文件；复制不可用时可手动选中文本。面板展示的是打开或刷新时的快照。

可选填“哪里困惑、卡住或觉得不公平”，这段反馈随复制/下载JSON一同导出。反馈只对应当前面板快照，自动保存的上一局不包含尚未导出的面板备注。重开或死亡时会尝试把最近一局保存到本机 `geoguard-last-playtest`，在面板点「上一局」可以取回；仅保留一份，存储不足时不会阻止游戏。刷新网页会丢失未结束的内存采集，建议途中定期导出。没有自动上传、账户标识、完整UA或网页浏览记录。

## 数据与决策问题

| 优化问题 | 记录 | 使用方式 |
| --- | --- | --- |
| 玩家为何受伤/死亡 | 每次有效HP伤害、目标位置、附近敌人数、危险区/接触或技能来源类别、最后血量 | 对齐操作与危险区快照，检查是否在建造、拾取、拥挤或避让阶段受伤 |
| 塔阵是否过脆、布局是否失误 | 塔类型、等级、坐标、创建/移除、塔受伤、建造尝试与拒绝原因 | 对比密集/分散塔阵、补建成本、失败建造和全灭节点 |
| 经济是否导致无法恢复 | 每笔资金变化、拾取/建造/奖励/击败结算来源、余额、地面未拾取水晶数量与价值 | 区分确实缺钱、钱在地上没拾取、有钱没建塔、建塔选择错误 |
| 兵线是否积压或出现空转 | 出生/明确击败/移除事件；两秒采样的总数、类型、屏内数、射程附近数、剩余生成队列、敌人位置 | 统计清线耗时、拥挤节点、敌人滞留和长期局部空场 |
| Boss反制是否可执行 | Boss位置/血量/阶段/蓄力-攻击-恢复状态、施放技能事件、屏外时间、最长未受伤时段 | 判断玩家是否错过恢复窗口、逃离后未接战，还是输出不足 |
| 奖励是否转化为有效策略 | 提供的奖励卡和选择、解锁蓝图、后续建造类型 | 检查选择解锁后是否实际建造，与推进和损塔表现关联 |
| 操作负担与设备体验 | 移动方向变化、输入设备、移动/静止时间、实际路程、拖塔开始与落点、视口变化 | 定位频繁转向、持续逃跑、建造中断、窄屏局部压力 |
| 卡顿是否影响判断 | 战斗期间原始RAF帧间隔数量、总耗时、超过50ms次数、最大间隔 | 对照高实体数阶段与卡顿，物理步长被夹断也不会掩盖原始帧间隔 |
| 主观困惑来自哪里 | 玩家自填备注、暂停/恢复、切后台时间 | 把“没看懂、找不到、觉得不公平”与实际局面对应，而不是从轨迹猜情绪 |

## JSON结构与时间

- `sessionId/build/mode/metadata`：单局ID、版本、正常/调试、初始视口与触控能力。部署时可通过 `VITE_BUILD_ID` 注入提交或发布版本；未注入则标注 `0.1.0-local`，不能据此区分多个本地代码版本。
- `events`：操作、波次、实体、伤害、资金、Boss与奖励事件。
- `samples`：每两秒采样，导出时额外截取当前状态；包括玩家/镜头、兵线位置、Boss、塔阵、蓝图、掉落和危险区。
- `waves`：每波累计出生/击败、建塔/失塔、有效HP伤害、资金变化、移动/静止、Boss屏外与最长未受伤时间，及最后状态。
- `performance`：战斗帧间隔汇总，暂停/奖励/后台时间不算战斗帧。
- `current/final/outcome`：当前或冻结的结束状态，区分进行中、死亡、重开；途中导出不会结束本局。
- `playerFeedback`：导出面板自填反馈。

事件和快照均包含UTC ISO `timestamp`、从开局计算的 `wallSeconds`、仅战斗推进的 `battleSeconds`、波次 `wave`。暂停、奖励期间现实时间继续而战斗时间冻结，可计算选奖励耗时与中断；同一会话多次导出会包含重叠内容，研究时应按sessionId使用最新快照，不能把它们当成多位玩家或多局。

## 统计口径与边界

出生指首次被采集器观察到实体；出生/移除采用每帧集合差分，极短同帧生成又移除的实体可能漏记。明确击败独立记录，消耗/牺牲和普通移除不直接当击杀；不要把 `enemy_removed` 再加到 `enemy_defeated`。塔移除在正常模式视为损塔；调试清场会混入，因此调试局必须单独分析。

HP伤害取扣血前后有效血量差，排除致死溢出，恢复后可以再次累计。敌方输出汇总目前不区分具体攻击者；玩家受伤来源只区分预警危险区与接触/技能上下文，不能精确声称由某个Boss某一招命中。`defeat-settlement` 包含Boss赏金和部分机制结算，不应全部算普通击杀收入；其他扣款/退款归入 `runtime-unclassified`，需结合Boss技能事件解释。统计不构成逐帧确定性回放，也不提供真人反应速度的精确测量。

移动方向变化最多每0.1战斗秒记录一次；短于此间隔的变化可能合并，不记录每次鼠标像素移动或每次无效按键。状态两秒采样不足以单独判断一次短预警是否被看见，必须结合伤害、Boss状态事件与玩家备注。

事件上限20,000条、状态上限3,600条（常规约两小时），超过后丢弃最老记录，`truncation`明示丢弃数量；每波累计仍保留。频繁手动刷新也占用采样容量。数据较大时优先发送下载的JSON文件。页面内存采集不改动正式游戏对象属性或随机序列。

## 后续真人试玩建议

先让玩家自然玩一局，不预先教授Boss最优解；在出现困惑或结束时导出，并写一句原因。后续使用新的session对照“有引导/无引导”“分散/集中塔阵”等单一改变。观察第一次受伤、第一次损塔、全灭后恢复、第一/第三波用时、Boss无输出空转、奖励解锁后使用情况。

真实玩家不能像模拟器一样精确认识所有几何。几局数据先用于发现模式，不估计总体胜率；不能以某位玩家不使用新塔就证明塔弱。若截断、调试模式、版本不明或反复导出的重叠数据存在，应先清理再比较。
